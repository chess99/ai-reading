# Topic Production Guide

本文档用于生产和更新主题阅读文章。全景计划 `docs/superpowers/plans/2026-06-01-topic-reading-panorama.md` 可以继续提供主题地图和历史 Reading Path，但**当前书单策展规则以 `docs/topic-curation-policy.md` 为准**。

它是主题文章生产指南，不是书籍入库指南。书籍文件命名、frontmatter、微信读书链接等仍遵守仓库根目录 `AGENTS.md`。

## 先判断任务类型

开始工作前，controller 必须先判断这一轮是“写作生产”还是“策展迭代”。两种任务不要混为一谈。

### 写作生产

当任务已经给出一份明确、已批准的书单，只要求把它写成主题文章时：

- worker 只负责解释读者问题、阅读梯度和每本书的角色；
- 不自行增删、替换或重排书籍；
- 不编造作者、slug、path、馆藏状态或微信读书链接；
- controller 负责把已批准的书单和必要元数据提供给 worker。

### 策展迭代

当任务明确要求审查、扩展、重构或更新一个主题书单时：

- 先读 `docs/topic-curation-policy.md`；
- 可以增删、替换、降级、升级和重排书籍；
- **不受 5–6、7–8、9–10 或任何固定本数限制**；
- 书单长度由读者问题和必要角色决定，书多本身不是拆主题的理由；
- 缺少完整书籍提炼但明确值得推荐的书，可以使用 `status: planned`，不得伪造 slug/path；
- 对强平台、强制度、强文化语境的主题，要主动检查中国语境是否缺位。

历史全景计划中的 Reading Path 是重要的策展起点，但不是永久冻结的书单。

## 适用的 Agent 分工

`superpowers:subagent-driven-development` 适合批量生产主题，但建议把角色拆开：

- **curator**：只在明确的策展任务中工作，负责选书、角色覆盖、顺序和主题边界；
- **writing worker**：拿到已批准书单后，只负责写一篇主题文章；
- **规格 reviewer**：检查文章是否符合当前批准书单、主题边界和仓库规范；
- **风格 reviewer**：检查结构、语气、重复感、边界说明和读者可读性。

不要让同一个 worker 一次生产多个无关领域主题。也不要让纯写作 worker 顺手补书籍提炼或修改全站分类。

## Worker 输入包

controller 给每个 worker 的输入应尽量收窄到当前主题，至少包括：

- 目标主题标题；
- 目标 slug 或既有文件路径；
- 当前批准的 `books:` 列表及顺序；
- 每本书的角色与推荐理由（如果已经策展完成）；
- 主题边界和必要的迁移说明；
- 是新建主题，还是更新既有主题；
- 本指南的必要部分。

如果这一轮是策展迭代，还应提供 `docs/topic-curation-policy.md` 和现有主题全文。没有明确策展授权时，writing worker 不应把历史计划当成邀请，自行扩展书单。

## Worker 输出

每个主题输出一篇 Markdown 主题文章。

完整主题文件的 frontmatter 建议使用：

```yaml
---
slug: <topic slug>
title: <topic title>
description: <一句话描述，从读者问题出发>
tags: [标签1, 标签2, 标签3]
date: 'YYYY-MM-DD'
books:
  - title: <书名>
    author: <作者>
    role: <短角色>
    reason: <one sentence>
    status: planned
---
```

已有高质量书籍提炼时使用：

```yaml
  - title: <书名>
    author: <作者>
    slug: <真实 slug>
    path: <真实 books/... 路径>
    role: <短角色>
    reason: <one sentence>
    status: in_library
```

如果 controller 没有提供可靠的作者、slug 或书籍文件信息，worker 不得猜测。`planned` 推荐可以没有 slug/path，后续完成书籍提炼后再升级为 `in_library`。

## 文章结构

主题文章没有固定的小节数量，也不根据书本数量机械决定篇幅。结构应由阅读路径的阶段决定。

常见骨架可以是：

```markdown
# <中文主题标题>

<开头：读者面对的问题，为什么这个问题难，这条路径要解决什么。>

<路径概览：从哪里进入，经过哪些阶段，最后抵达什么系统或边界。>

## <阶段一：入口或实践起点>

<解释这一阶段解决什么问题，相关书分别增加什么。>

## <阶段二：核心框架或方法>

<说明为什么需要从上一阶段继续推进。>

## <阶段三：系统、经营、风险或批判>

<把个人行动放回更大的结构。>

## 建议读法

<按读者阶段给出具体阅读策略和带入书中的问题。>
```

一条路径可以只有三个阶段，也可以有五六个阶段。只要所有阶段仍服务同一个读者目标，就不因为书多而拆分。

无论结构如何变化，都应保留这条功能线：

1. 读者问题；
2. 路径概览；
3. 入口或行动起点；
4. 核心框架；
5. 实践、系统、风险或批判；
6. 建议读法。

## 写作风格

写得像谨慎的编辑，不像营销文案。

应该使用：

- 清楚但不过度的判断；
- 具体的读者处境；
- 短段落；
- 因果语言：因为、所以、如果、当；
- 克制的中文，不堆概念。

避免使用：

- 夸张词：`必读`、`颠覆认知`、`人生必备`、`底层逻辑`、`认知升级`、`闭环`、`赋能`；
- 空泛赞美：`这本书非常经典`、`值得每个人读`、`内容很系统`；
- 可以套在任何书上的通用摘要；
- 很长的抽象开场；
- 把所有主题都写成自我提升建议；
- 每本书都用同一种句式介绍。

好的开头从真实张力开始，例如：

- 重大决策之所以难，是因为流程、偏见、不确定性和后果会同时发生作用。
- 产品从 0 到 1 的难点通常不在功能实现，而在团队很容易把“做出来”误当成“被验证”。
- 创伤修复难，是因为理解过去并不会自动恢复安全感。

差的开头从空泛重要性开始，例如：

- `在现代社会中，决策能力越来越重要。`
- `产品能力是每个创业者必须掌握的核心能力。`
- `心理健康已经成为当代人不可忽视的话题。`

## 书籍处理规则

使用**当前批准的主题书单**，而不是默认把某份历史 plan 当成不可修改的唯一真相。

如果这一轮只是写作生产，当前批准书单通常就是 controller 给出的列表，worker 必须保持顺序。若这一轮是策展迭代，则先按 `docs/topic-curation-policy.md` 完成选书和顺序，再把结果交给 writing worker。

解释每本书在这条路径中的角色，而不是泛泛评价。一个好的说明应回答：

- 这本书在这条路径中处理什么问题？
- 为什么它出现在这个位置？
- 它比前面的书多增加了哪一层？
- 如果删除它，会缺少什么关键角色？

如果最后一个问题没有明确答案，这本书很可能只是重复，应考虑删除或降为延伸阅读。

同一本书出现在不同主题中时，必须围绕当前主题重新定位。例如：

- 《系统之美》在重大决策主题中：后果、反馈和意外效应；
- 《系统之美》在复杂性主题中：存量、流量、反馈回路和杠杆点；
- 《身体从未忘记》在创伤主题中：身体记忆和安全感恢复；
- 《身体从未忘记》在关系安全主题中：冲突和亲密关系中的创伤反应。

## 边界说明

边界说明放在正文里，不要写进标题。敏感领域需要在开头附近直接说明。

### 心理健康

```markdown
这条阅读路径只用于理解问题和组织自我观察，不替代专业医疗、心理咨询或危机干预。如果已经出现自伤念头、持续失眠、明显功能受损、暴力风险或现实危机，应优先寻求专业支持和身边可信任的人帮助。
```

### 医疗、营养与运动

```markdown
这条阅读路径只用于建立健康理解，不提供诊断、治疗、营养处方或运动处方。涉及疾病、用药、减重、控糖、慢性疼痛或训练伤病时，应以专业医生或合格专业人士建议为准。
```

### 法律

```markdown
这条阅读路径只用于建立法律常识，不构成法律建议。遇到具体纠纷、合同、刑事风险或诉讼问题，应咨询合格法律专业人士。
```

### 投资与交易

```markdown
这条阅读路径只用于理解投资、交易、周期和风险，不构成投资建议，也不鼓励照搬任何交易方法。真实资金决策需要独立判断、风险承受能力评估和必要的专业咨询。
```

### AI

```markdown
AI 工具和模型变化很快，这条阅读路径只提供理解框架。使用 AI 输出时需要独立核验，不应把模型回答当作专业判断、事实来源或最终决策依据。
```

## 标题规则

标题应该让浏览网站的读者知道页面能帮他解决什么。历史计划中的标题可以作为默认值，但明确的策展迭代允许在不改变主题目标的前提下优化标题。

好的标题：

- `如何理解交易、周期与市场风险`
- `理解焦虑与抑郁`
- `如何识别偏见、从众与服从`
- `产品从 0 到 1`

避免防御化、说教化或为了显得深刻而改成反问。

## 一致性检查清单

worker 返回前必须自查：

- 标题、slug 和主题目标一致；
- 书籍与**当前批准书单**一致；
- 若为写作生产，没有擅自策展；
- 若为策展迭代，已经按 `docs/topic-curation-policy.md` 检查角色覆盖、冗余、本土语境和拆分条件；
- 没有为了固定数量凑书或删书；
- 开头从读者问题开始；
- 文章解释了路径梯度；
- 每本书都说明了它在路径中的角色；
- 敏感主题包含必要边界说明；
- 没有营销词、套话和空泛赞美；
- 结尾给出了具体读法；
- 没有编造书籍馆藏信息。

## Reviewer Rubric

规格 reviewer 检查：

- 主题标题、slug/file 是否匹配当前任务；
- 书籍顺序是否匹配当前批准书单；
- 写作任务中是否出现未经授权的策划改动；
- 策展任务中是否违反 `docs/topic-curation-policy.md`；
- 必要边界说明是否出现。

风格 reviewer 检查：

- 开头是否问题优先；
- 小节是否形成清晰递进；
- 语言是否具体、克制；
- 书籍说明是否基于角色，而不是泛泛评价；
- 和既有主题页相比，语气是否一致。

如果任一 reviewer 发现问题，交回对应 worker 修改，再复查。

## Controller 操作流程

### 写作生产

1. 从当前批准的主题清单中取一个主题；
2. 构造最小输入包；
3. 派发 writing worker；
4. 派发规格 reviewer；
5. 修正后派发风格 reviewer；
6. controller 最后统一落盘、检查 Markdown/frontmatter，并提交本轮变更。

### 策展迭代

1. 读取现有主题与 `docs/topic-curation-policy.md`；
2. curator 明确读者问题和缺失角色；
3. 增删、替换、重排并决定 `planned` / `in_library`；
4. reviewer 检查是否存在重复、语境缺口或错误拆分；
5. 将批准后的书单交给 writing worker 重写正文；
6. controller 校验 frontmatter、真实路径和站点兼容性，并提交本轮变更。

controller 不应把无关历史争论、被否决的调整或其他主题文件塞给 worker。worker 只需要完成当前角色所需的上下文。
