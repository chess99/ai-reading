# Topic Production Guide

本文档用于从 `docs/superpowers/plans/2026-06-01-topic-reading-panorama.md` 批量生产主题文章。

它是主题文章生产指南，不是书籍入库指南。当前阶段，写作 worker 不检查书籍是否存在于 `books/`，不新增书籍提炼，不更新 `book-scores.md`，也不重新策划全景书单。

## 适用判断

`superpowers:subagent-driven-development` 适合用来执行这批主题生产，但要按“写作生产”改造，而不是照搬代码实现流程。

适合的原因：

- 已经有明确 plan：全景计划文件就是批次计划。
- 主题之间大多独立：每篇主题文章可以单独写、单独审。
- worker 需要干净上下文：只给它目标主题、对应书单、梯度说明和本指南，避免它被历史讨论带偏。
- 每个任务都能做双审：先审是否符合 plan，再审写作质量和风格。

不适合让 subagent 做的事：

- 重新判断主题分类是否合理。
- 增删、替换、重排书单。
- 检查 `books/` 中是否已有书籍。
- 顺手补书籍提炼、作者、slug、评分。
- 一次性生产多个跨领域主题。

后续生产时，主 agent 是 controller；子 agent 是纯粹的主题文章写作工人。

## 生产目标

把全景计划中的每一行已批准主题，写成一篇面向读者的主题文章。

worker 的工作是写作：

- 解释这个主题要解决的读者问题。
- 让阅读路径显得有意图，而不是一串书名。
- 说明为什么这些书按这个顺序读。
- 给出具体读法和阅读时要带着的问题。
- 保留 plan 中的主题标题、书单顺序、迁移决定和边界定位。

worker 不是 curator。除非全景计划明确要求，否则不得新增、删除、替换、重排、改名或降级任何书。

## Worker 输入包

controller 给每个 worker 的输入必须收窄到当前主题。

每个 worker 必须收到：

- 目标主题标题。
- 目标 slug 或既有文件路径。
- 全景计划中的原始行：`Layer`、`Topic`、`Reading Path`、`Gradient`。
- 重构矩阵里的迁移指令。
- 适用的领域边界说明。
- 是新建主题文章，还是更新现有主题文章。
- 本文档全文或必要摘录。

worker 不应读取整个仓库。若是更新现有主题，controller 应只提供该主题文件，或明确要求 worker 只读该文件。

## Worker 输出

每个主题输出一篇 Markdown 主题文章。

如果是完整主题文件，建议 frontmatter 使用这个形状：

```yaml
---
slug: <topic slug>
title: <topic title>
description: <一句话描述，从读者问题出发>
tags: [标签1, 标签2, 标签3]
date: 'YYYY-MM-DD'
books:
  - title: <书名>
    author: <作者，未知时由 controller 后续补齐>
    role: <短角色>
    reason: <one sentence>
    status: planned
---
```

如果 controller 没有提供作者、slug 或书籍文件信息，worker 可以让书籍元数据保持不完整。不得编造作者名、书籍 slug 或馆藏状态。后续入库或发布整理阶段再统一补齐，并把推荐关系转换为 `status: in_library`。

如果 controller 提供了现有 `books:` 区块，worker 应保留它，除非全景计划明确要求修改。

## 文章结构

默认正文结构：

```markdown
# <中文主题标题>

<开头：读者面对的问题，为什么这个问题难，以及这条路径能澄清什么。>

<路径概览：用一段话说明这条路径如何从入口、框架走到系统/实践/批判。>

## 入口：<入口问题>

<解释前 1-2 本书作为入口的作用。说明读者先看见什么。>

## 框架：<核心模型>

<解释中段书籍如何建立概念框架、实践框架或判断框架。说明每本书增加了哪一层。>

## 系统：<更大的背景、约束或批判>

<解释后段书籍如何连接系统、风险、制度、长期后果、复杂性或高阶实践。>

## 建议读法

<给出具体阅读策略，以及 3-5 个读者可以带进书里的问题。>
```

小型 5-6 本主题可以压缩成三个正文小节。复杂 9-10 本主题可以扩展到四个正文小节。无论结构如何变化，都必须保留这条功能线：

1. 读者问题。
2. 路径概览。
3. 入口书籍。
4. 核心框架书籍。
5. 系统、实践或批判书籍。
6. 建议读法。

## 写作风格

写得像谨慎的编辑，不像营销文案。

应该使用：

- 清楚但不过度的判断。
- 具体的读者处境。
- 短段落。
- 因果语言：因为、所以、如果、当。
- 克制的中文，不堆概念。

避免使用：

- 夸张词：`必读`、`颠覆认知`、`人生必备`、`底层逻辑`、`认知升级`、`闭环`、`赋能`。
- 空泛赞美：`这本书非常经典`、`值得每个人读`、`内容很系统`。
- 可以套在任何书上的通用摘要。
- 很长的抽象开场，比如从社会、时代、成长泛泛说起。
- 把所有主题都写成自我提升建议。
- 每本书都用同一种句式介绍。

好的开头从真实张力开始：

- 重大决策之所以难，是因为流程、偏见、不确定性和后果会同时发生作用。
- 产品从 0 到 1 难，不是因为没人会做功能，而是因为团队很容易把“做出来”误当成“被验证”。
- 创伤修复难，是因为理解过去并不会自动恢复安全感。

差的开头从空泛重要性开始：

- `在现代社会中，决策能力越来越重要。`
- `产品能力是每个创业者必须掌握的核心能力。`
- `心理健康已经成为当代人不可忽视的话题。`

## 书籍处理规则

使用 plan 里的书籍顺序。

解释每本书在这条路径中的角色，而不是泛泛评价这本书。一个好的说明应回答：

- 这本书在这条路径中处理什么问题？
- 为什么它出现在这个位置？
- 它比前面的书多增加了哪一层？

不要把主题文章写成每本书的独立小书评。主题文章的主语是“阅读路径”，不是“书评合集”。

同一本书出现在不同主题中时，必须围绕当前主题重新定位。例如：

- 《系统之美》在重大决策主题中：后果、反馈和意外效应。
- 《系统之美》在复杂性主题中：存量、流量、反馈回路和杠杆点。
- 《身体从未忘记》在创伤主题中：身体记忆和安全感恢复。
- 《身体从未忘记》在关系安全主题中：冲突和亲密关系中的创伤反应。

## 边界说明

边界说明放在正文里，不要写进标题。

敏感领域需要在开头附近放一段直接说明。

### 心理健康

```markdown
这条阅读路径只用于理解问题和组织自我观察，不替代专业医疗、心理咨询或危机干预。如果已经出现自伤念头、持续失眠、明显功能受损、暴力风险或现实危机，应优先寻求专业支持和身边可信任的人帮助。
```

### 医疗、营养与运动

```markdown
这条阅读路径只用于建立健康理解，不提供诊断、治疗、营养处方或运动处方。涉及疾病、用药、减重、控糖、慢性疼痛或训练伤病时，应以专业医生或合格专业人士建议为准。
```

### 法律

```markdown
这条阅读路径只用于建立法律常识，不构成法律建议。遇到具体纠纷、合同、刑事风险或诉讼问题，应咨询合格法律专业人士。
```

### 投资与交易

```markdown
这条阅读路径只用于理解投资、交易、周期和风险，不构成投资建议，也不鼓励照搬任何交易方法。真实资金决策需要独立判断、风险承受能力评估和必要的专业咨询。
```

### AI

```markdown
AI 工具和模型变化很快，这条阅读路径只提供理解框架。使用 AI 输出时需要独立核验，不应把模型回答当作专业判断、事实来源或最终决策依据。
```

## 标题规则

除非全景计划明确修改，使用 plan 中的主题标题。

标题不要防御化、说教化，也不要为了显得深刻而改成反问。标题应该让正在浏览网站的读者知道这篇文章能帮他解决什么。

好的标题：

- `如何理解交易、周期与市场风险`
- `理解焦虑与抑郁`
- `如何识别偏见、从众与服从`
- `产品从 0 到 1`

差的标题：

- `为什么交易很难与市场风险`
- `理解焦虑与抑郁的自助边界`
- `为什么人会偏见、从众与服从`，当页面目标其实是帮助读者识别和应对偏见、从众与服从时。

## 一致性检查清单

worker 返回前必须自查：

- 标题和分配主题一致。
- 书籍顺序和 plan 一致。
- 没有未经授权新增、删除、替换、改名或重排书籍。
- 开头从读者问题开始，而不是从“这个主题很重要”开始。
- 文章解释了路径梯度。
- 每本书都说明了它在路径中的角色。
- 敏感主题包含必要边界说明。
- 没有营销词、套话和空泛赞美。
- 结尾给出了具体读法。
- 文章不讨论书籍是否存在于 `books/`。

## 推荐子 Agent 分工

全景计划锁定后，再使用子 agent 批量生产。

推荐每个主题使用三类角色：

- 写作 worker：只负责写一篇主题文章。
- 规格 reviewer：只检查文章是否符合该主题的 plan 行和本指南。
- 风格 reviewer：只检查语气、结构、重复感、边界说明和读者可读性。

不要让同一个 worker 一次生产多个无关领域的主题。不要让 worker 同时承担策划、入库和写作。

## Reviewer Rubric

规格 reviewer 检查：

- 主题标题、slug/file、书籍顺序是否匹配批次计划。
- 迁移指令是否执行。
- 是否出现未经授权的策划改动。
- 必要边界说明是否出现。

风格 reviewer 检查：

- 开头是否问题优先。
- 小节是否形成入口 -> 框架 -> 系统/实践的递进。
- 语言是否具体、克制。
- 书籍说明是否基于角色，而不是泛泛评价。
- 和既有主题页相比，语气是否一致。

如果任一 reviewer 发现问题，交回同一个 worker 修改，再由对应 reviewer 复查。

## Controller 操作流程

controller 每次从全景计划中取一个主题，构造一个最小输入包，然后派发 worker。

推荐流程：

1. 读取全景计划，抽取全部待生产主题。
2. 对每个主题生成独立任务包。
3. 派发一个干净 worker 写作。
4. 派发规格 reviewer 审查。
5. 若规格不合格，交回同一个 worker 修改，再复审。
6. 派发风格 reviewer 审查。
7. 若风格不合格，交回同一个 worker 修改，再复审。
8. controller 最后统一落盘、检查 Markdown/frontmatter，并提交本批次变更。

controller 不应把历史争论、被否决的 v9.1 调整、其他主题文件或 `books/` 上下文塞给 worker。worker 只需要当前主题的 plan 行和本指南。
